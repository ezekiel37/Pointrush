# Authentication foundation

Status: authentication is now mounted only when the complete production configuration is present. Better Auth 1.7.6 owns password hashing, verification, reset tokens and database-backed sessions; Resend is the selected email delivery implementation. No live email has been sent or provider account configured.

## Implemented boundaries

- Authentication uses separate PostgreSQL tables, migrated by Drizzle with the existing application migration runner. Better Auth's credential `account` model is explicitly mapped to `auth_credentials`, never PointRush `accounts`.
- Signup creates only an authentication identity. It does not claim a username, verify a phone, establish legal identity, grant a role or approve a sponsor.
- `POST /api/v1/accounts/me` is the authenticated onboarding command. It derives the auth user from the session and atomically creates the PointRush account, profile, username and one-to-one identity link. Retrying a successful command cannot create a second PointRush account.
- Onboarding locks the auth identity and rechecks email verification within the transaction. Identical retries return the existing identity; changed onboarding data returns 409. Suspended, restricted and closed accounts are denied by the Nest session guard except for the explicit private account-status read. The transaction also checks account state when returning an existing onboarding result.
- `GET /api/v1/accounts/me` returns onboarding status and minimal account identity/access state derived solely from the session. Restricted accounts can read their own status without gaining other permissions. See [the response contract](ACCOUNTS.md#private-account-status).
- Nest routes require a verified session by default; only health routes are explicitly public. Mutating Nest requests additionally require an exact trusted Origin header, including non-browser clients. Authentication library routes retain their own origin checks. A session grants no sponsor/admin role: future business controllers must require their specific account and role permissions.
- Email verification is required before password login. Neither signup nor verification automatically creates a session.
- Passwords use Better Auth's default scrypt implementation, with a 15–128 character policy. No custom hashing or password/token logging.
- Password reset identifiers are stored hashed; successful resets revoke existing sessions. Cookie caching is disabled, so revoked sessions are checked against the database.
- Explicit origin allowlists; no wildcards. HTTPS is required except loopback development. Cookies are host-only, HTTP-only, SameSite=Lax and Secure on HTTPS. Cross-subdomain cookies and account linking are not enabled.
- Resend messages use plain text and never interpolate display names into HTML. Provider failures become a generic delivery error without leaking addresses or links. No console email fallback exists.
- Production module wiring reserves email quota before signup, reset or verification resend executes. Known and unknown addresses follow the same checks. It uses a 60-second recipient cooldown, three requests per recipient per hour, and a configurable global 24-hour cap (`AUTH_EMAIL_DAILY_LIMIT`, default 100; maximum 10000). These are conservative launch defaults, not provider-plan entitlements or money taken from reward backing. Invalid and duplicate requests may consume reservations even when no email is needed.
- Quota reservations use conditional PostgreSQL upserts in one transaction, ordered global then recipient. Recipient rejection rolls back the global reservation. All instances share counters; recipient keys are HMACs, with no email addresses or auth links stored in the budget table. Auth secret rotation resets recipient pseudonyms but preserves the global cap.
- Email quota errors fail closed before queuing: 429 for a limit, 503 for unavailable quota storage. The API queues encrypted mail; provider outages are handled by a separate worker and retain the original reservation. Worker `accepted` outcomes mean provider acceptance, not inbox delivery. Timing resistance is not established. See [queue operations and failure boundaries](EMAIL_QUEUE.md).
- Transport is bounded to two attempts, each with a 5-second abort deadline and 250 ms retry delay. The same payload and idempotency key are reused within those attempts. Authentication/validation/rate-limit errors and explicit provider backoff are not retried inline. The small Resend HTTP boundary uses the documented API because the pinned SDK logs raw provider errors outside production and does not expose a typed abort signal for sending.
- Login attempts no longer automatically resend verification email. The client must offer an explicit verification resend action. Quota controls run before Better Auth opens its signup transaction, avoiding nested database acquisition from the mail callback.
- Built-in auth logging is disabled to avoid accidental sensitive payload logging. Safe structured security-event logging is a release gate, not implemented here.

Security defaults in this slice: verification link 1 hour; reset link 30 minutes; sessions 7 days with daily refresh. These are configuration choices, not promises of final launch policy. Fresh authentication for sensitive actions still needs implementation.

## Required before public launch

1. Production startup validates exact HTTPS auth/trusted/CORS origins, sender shape, auth-secret length and queue encryption key. Non-production HTTP is permitted only on loopback. Generate a high-entropy auth secret (length is not entropy), provide it to the API and the Resend key only to the delivery worker, verify the sender domain, and use a stable API origin. Define rotation and recovery procedures. The API's four required auth settings are AUTH_SECRET, AUTH_BASE_URL, EMAIL_FROM and AUTH_EMAIL_ENCRYPTION_KEY; origin and database requirements remain separate.
2. The handler is mounted before ordinary Nest parsers with a 64 KiB stream limit, request IDs, security headers and credentialed exact-origin CORS. Real Nest/Express integration tests cover signup, verification, login, protected routes, onboarding, malformed/oversized bodies and signout. Browser cookie delivery still needs deployment testing.
3. The HTTP boundary replaces client-supplied `x-pointrush-client-ip` with the direct socket address. This prevents spoofing, but behind Cloudflare/Cloud Run it may group many users under a proxy address. Validate the full ingress chain, direct-origin bypass controls and trusted client-IP policy before public launch. Never accept arbitrary forwarding headers as authoritative.
4. Built-in rate limits use PostgreSQL storage (30 requests per minute, plus library endpoint-specific defaults). This is not proof of race-safe distributed abuse prevention. Verify multi-instance concurrency and implement atomic abuse controls, per-account/email throttles, cost limits and cleanup before public signup.
5. Default-deny Nest session protection and retry-safe onboarding are implemented. Add role-specific permission guards as business routes are introduced. Financial and other sensitive writes must recheck authorization/account status inside their transaction; a request-start guard alone cannot prevent a concurrent suspension race.
6. Durable encrypted mail queuing and bounded worker retries are implemented. Configure worker invocation before enabling signup. Delivery webhooks, bounce handling, welcome emails and cleanup of stale budget rows remain unimplemented. Prolonged outages can outlast link expiry; users then need a new request. UI copy must not promise inbox delivery. Test timing-based enumeration and native multi-instance behavior before launch. Attackers may exhaust the shared cap and delay legitimate requests; layered bot controls and operational alerting remain necessary.
7. Add MFA/step-up protection for administrators and sensitive actions; session management UI; safe security audit events; expired-record cleanup; retention policies. Database session tokens remain sensitive bearer material in the library's storage model: restrict database/backup access and never expose or log rows.
8. Run native PostgreSQL and deployed-browser integration tests. The automated auth tests use the real library and PGlite PostgreSQL, but cannot prove network pool behavior, native concurrency, browser cookie behavior or provider delivery. Readiness checks required account/auth tables including the mail queue; it does not prove that a worker is running or the provider is reachable.

## Local verification

`npm run check` covers auth config rejection, signup isolation, stored password hashing, unverified login rejection, email verification, cookie attributes, reset token replay rejection, session revocation, expired sessions, untrusted origins and redirects, password bounds, reset-response parity, and email template/sender validation. Test email is captured only in an in-memory mailbox; no real Resend request is made.

Integration was also checked against the pinned installed package types and implementation.

Resend's documented [idempotency keys](https://resend.com/changelog/idempotency-keys) are retained for 24 hours. Queue retries preserve the same key and payload within a 20-minute job lifetime. Native quota and worker concurrency tests are present in `test:db` but have not been executed in this workspace. PGlite exercises rollback, caps, cooldown and outage responses without proving native pool concurrency.
